# Mac Settings and the Windows/Linux settings page

Every control of the Mac app's Settings window (Sources/MiniGateway/Settings.swift) and its counterpart in
`minigw serve` (the settings page `/minigw/settings`, the admin API in [admin-api.md](admin-api.md) and
`serve.json`). Mac only: Siri AI, Apple Foundation Models, the WebDAV folder mount (direct mode), native mode,
`minigw run`, and the build network switches of worktree mode.

Search and Clear only in the Mac window. |

| Claude CLI · May ask other models | same | `agents/{claude,codex,grok,copilot}.askOthers`, `gw claude --ask-others` | Off by default, on every agent pane. A loopback port and token per run; the asked agent works in the caller's folder; one level deep, never its own kind. Grok: its `--sandbox workspace` reaches the run port directly (verified). Claude: through its sandbox proxy (macOS, and Linux with Claude Code's bwrap/socat sandbox). Windows (no sandbox): the instructions say `minigw -p …` (the run's PATH starts with the folder of `minigw.exe`, also when the tray runs the gateway) and only `minigw -p` and `minigw models` are pre-approved (as `Bash(…)` and `PowerShell(…)` rules), unless that folder is inside an allowed folder, the session folder or Scratch (an agent could plant `minigw` or `git.exe` there): then the instructions name `minigw.exe` by its full path and nothing is pre-approved; other Bash commands (also `git commit`) still need approval, so the agent cannot run them. A chain such as `minigw -p x; whoami` runs because Claude Code checks each part on its own: `whoami`, `git status` are its built-in read-only commands and `Set-Content` in the working folder is allowed by `acceptEdits` (Allow local tools); the `minigw` rule allows no other part (Claude Code 2.1.318). |

| General · Worktree mode: Network for builds, Network for Codex builds | – | `worktreeNetwork` (Mac config) | Worktree mode itself works on both (`--minigw-work=worktree`, mirrors in `scratch/repos`, clones in `scratch/worktrees`).
