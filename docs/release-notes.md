# Release notes

## Unreleased

- Fixed (#67, Mac app): in worktree mode with "May ask other models" off, Claude's sandbox could not run the gateway's git wrapper, so `git clone` in the clone failed with "could not lock config file … Operation not permitted" instead of the `$MINIGW_DEPS` hint, a clone of a remote URL into `$MINIGW_DEPS` failed with "git: 'remote-https' is not a git command", and CMake FetchContent could not run its `GIT_EXECUTABLE`. The wrapper is now readable in the sandbox for every worktree run. The agent's instructions give the CMake, SwiftPM and Xcode recipes with the literal folder path, because Claude Code refuses a command with `$MINIGW_DEPS` in it ("A variable in this command can't be checked before it runs"); the git refusal hint does the same (both gateways).
- New (#67): in worktree mode each conversation's agents get a dependencies folder `$MINIGW_DEPS` next to their clone under the gateway's Scratch folder. Repositories an agent creates (`git init`, `git clone`, CMake FetchContent with git sources, SwiftPM checkouts) work there, kept for the whole conversation and removed with the clone; anywhere else, also inside the clone, git refuses with a hint (`cmake -DFETCHCONTENT_BASE_DIR="$MINIGW_DEPS/cmake"`, `swift build --scratch-path "$MINIGW_DEPS/swiftpm"`), the same for every agent. This replaces the 0.5.22 limitation. Only agents that may write get it; a `git clone` of a remote URL with the agent's build network off is refused with the setting's name. Windows gateways have no agent sandbox yet, so there agents cannot create repositories (the agent note says so).
- Changed (#67): everything agent builds write stays under the Scratch folder: Claude Code's temporary folder (`CLAUDE_CODE_TMPDIR`), the project's Maven repository (as before), shared download caches per project for Go modules (`GOMODCACHE`), npm and pip, and the Go build cache (`GOCACHE`), Cargo (`CARGO_HOME`) and Gradle (`GRADLE_USER_HOME`) per conversation. Agents in worktree mode can no longer write `/tmp` (Mac: Claude, Codex; Linux: Codex). Before every run the gateway checks that the folders an agent may write are still real folders of the gateway user, and makes a replaced one again, so a link planted by an earlier run cannot open another folder to the sandbox. Claude Code's temporary folder is a short link in a private `/tmp/mgw-…` folder that points into `$MINIGW_DEPS/tmp`, because Claude Code needs a short path for its sockets; its files (also those of commands in its sandbox) stay under Scratch. On `minigw serve` the Claude run's `TMPDIR`, which was a folder under `/tmp`, is now the same kind of link (Windows: `$MINIGW_DEPS/tmp` itself); agents cannot write the link folders. If the link cannot be made, the run is refused. Both gateways.
- Fixed (#69): a gateway agent asked to "use codex to …" ran the `codex` program itself instead of asking the gateway (with "May ask other models" off, Claude Code's sandbox on the Mac stopped it at `~/.codex/config.toml` and Windows refused the command). Every gateway agent's instructions now say that other agents are reached only with `minigw -p --model …` and never by running `codex`, `claude`, `grok` or `copilot` directly; with "May ask other models" off they say other agents are not available here, so the agent does the task itself and says so. Mac app and `minigw serve`, every agent kind.
- Fixed (#70): on Windows `minigw serve` in worktree mode, Claude CLI tried `git add` and `git commit` in its clone, which need approval that `claude -p` cannot give, so they were refused (the Mac and Linux allow them through Claude Code's sandbox). On Windows the gateway commits the agent's work on its branch when the run ends, so the agent's instructions there now say "Do not run git add or git commit: the gateway commits your changes on this branch when you finish" (also for nested repositories; every agent kind). Git is not pre-approved on Windows, since git without a sandbox can run any command; the agent's own git commit needs the Windows sandbox (#68).
- Security (#24): every `minigw run` on the Mac gateway now keeps its temporary files in its own folder in the gateway's Scratch folder (`tmp/run-<id>`, removed when the run ends): `TMPDIR`, `TMP`, `TEMP`, the clang module cache and `java.io.tmpdir` of every Java process (`JAVA_TOOL_OPTIONS`, which replaces the `MAVEN_OPTS` setting, so Maven's forked test JVMs and Gradle get it too; Java prints "Picked up JAVA_TOOL_OPTIONS"). The build can no longer write the shared `/tmp`. Fixed with it: Maven tests that create temporary files failed in `minigw run` ("Operation not permitted"). The only writes outside Scratch are macOS's own save copies in the user temporary folder, because Foundation and the `swift build` link step ignore `TMPDIR` and no setting moves them: new `TemporaryItems/NSIRD_*` and `TemporaryDirectory.*` folders, never other files there, and existing ones cannot be renamed, deleted or replaced (see How it works, minigw run sandbox). `swift build` and `xcodebuild` work as before. Run folders left by a crash are removed when the app starts. A Scratch folder whose path contains a quotation mark is refused. Mac app only (`minigw serve` has no `minigw run`).
- New (#68): a Windows gateway (`minigw serve`, MSI) runs Claude CLI, Copilot and Grok in the Windows sandbox, Microsoft MXC 1.0.1 (`wxc-exec.exe` in the install folder's `mxc` subfolder, MIT license in `mxc\LICENSE.txt`, no admin rights; Windows 11 build 26100.9278 / 26200.9278 or later; an older build is named in the reason). The whole agent CLI runs in a container that writes only to the session's folder (when allowed), `$MINIGW_DEPS`, caches and its temporary folder under Scratch, reads only the program folders on `PATH`, and cannot read your home folder, other devices' copies or the gateway's settings. "Allow commands without a sandbox" is then not needed (shown as such); Claude runs commands with its PowerShell tool, commits its own work in worktree mode again (#70 now applies only without the sandbox) and can create repositories in `$MINIGW_DEPS` (`git.exe` there is minigw's wrapper). Claude starts each run with a fresh config and home under `Scratch\tmp` (only the conversation's transcript is kept under `Scratch\state`, so `--resume` works) and signs in with the token from `claude setup-token`; Grok gets its own home per device with your `auth.json` and `config.toml` copied in before a run, never back. Folders on `PATH` inside your home (for example `~\.local\bin`) are readable by agents; the settings page warns about them. Settings page → General → About and `minigw gw status` show "Agent sandbox: Windows sandbox (MXC 1.0.1)" or why it is not available; then everything works as in 0.5.22. minigw checks `wxc-exec.exe` against the SHA-256 it was built with before every use, keeps it open without write or delete sharing during a run and refuses an `mxc` folder with other files than `wxc-exec.exe` and `LICENSE.txt`; the probe checks that the box cannot read `admin.secret`. When the box cannot reach 127.0.0.1 (loopback may need a newer cumulative update) the sandbox stays available, but the gateway log and `minigw gw status` say that "May ask other models" does not work there. The `git.exe` wrapper copy under `Scratch\gitexec` is hash-checked, and stale copies are removed at start; the per-second `.git` check also runs in the box. The release build fetches MXC by its exact tag and pinned SHA-256 (`scripts/fetch-mxc.sh`). Codex cannot start inside MXC: on Windows it now runs without "Allow commands without a sandbox" when its own elevated sandbox is set up (`codex sandbox setup --elevated` once, as administrator), otherwise it still needs the switch. On Windows each Codex run then gets `-c windows.sandbox="elevated"`, and its `TEMP`/`TMP` is the run's folder under Scratch.
- New (#68, decision 7): **Network for builds** on `minigw serve` (settings page → General → Worktree mode, `minigw gw settings` → General, `PATCH general {"worktreeNetwork"}`; on by default), the same switch as on the Mac: off, Claude CLI's commands in worktree mode have no network (Linux: Claude Code's sandbox; Windows: the Windows sandbox, which allows only TCP 443 to the addresses of `api.anthropic.com` resolved when the run starts, so Claude's web fetch and web search fail, and a run is refused when the name cannot be resolved; without the Windows sandbox the switch has no effect) and a remote `git clone` is refused naming "Settings → General → Worktree mode → Network for builds".
- Changed (#68): on Windows, local tools or Bash/PowerShell in the tools without "Allow commands without a sandbox" no longer stop the gateway from loading its settings; without the Windows sandbox each request is refused with the same text instead.
- New (#68): a **Login** row for every agent on `minigw serve` (settings page and the Gateway tray's Settings window, en and sl; `minigw gw settings`; `minigw gw claude|codex|grok|copilot login`; admin API `GET /agents/{claude,codex,grok,copilot}` → `login`), showing only the state (set / not set / logged in) and a one-line hint, never the value. Agents use subscription logins by default and nothing is copied back from a run. Claude CLI: the long-lived token from `claude setup-token` (Claude subscription, valid one year) in Credential Manager or the key store, passed as `CLAUDE_CODE_OAUTH_TOKEN` (`minigw gw claude token [remove]`, settings page → Claude CLI → Login, `PATCH /agents/claude {"token"}`); in the Windows sandbox it is required ("Claude CLI in the Windows sandbox needs a long-lived sign-in token: run claude setup-token, then minigw gw claude token", 503) and `~\.claude` is never copied in. Codex: the ChatGPT login state from `~/.codex/auth.json`. Grok: logged in or `grok login` (after Grok refreshes its login you may need `grok login` again). Copilot: its existing token for commands now lives in the same row. Opt-in **Use an API key instead** (Claude CLI `ANTHROPIC_API_KEY`, Codex `CODEX_API_KEY`, Grok `XAI_API_KEY`; `minigw gw claude|codex|grok apikey [remove]`, `PATCH {"apiKey"}`): stored in the key store, passed only when set, billed through the provider's API, not your subscription. The Mac app needs none of this (Claude uses your Keychain login).
- Changed (#68): Claude CLI conversations on a Windows gateway from 0.5.22 start fresh once (Claude's sessions now live in the box's own folders, not in `~\.claude`).
- Security (#68): the Windows sandbox has no proxy (MXC's `allowedProxyPeer` is a package identity, not a host and port, and MXC's proxying on Windows covers only WinHTTP clients). Without network for builds Claude's box allows only TCP 443 to the `api.anthropic.com` addresses resolved at run start (logged). Loopback is denied unless "May ask other models" is on: then the box can reach all of this computer's 127.0.0.1 services, because the run port is there. The gateway still refuses the agent (the admin API refuses the gateway's agent processes, the main port needs the token, which the agent cannot read, and the run port accepts only that run's processes), but other local services such as LiteLLM or Foundry Local are reachable, so keep the switch off if agents should not reach them.
- Security (#68): API-key environment variables inherited from the gateway's own environment (`ANTHROPIC_*`, `OPENAI_API_KEY`, `CODEX_API_KEY`, `XAI_API_KEY`, `GROK_CODE_XAI_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`) no longer reach any agent run, so no agent is billed through an API by accident (`minigw serve` on Windows, Linux and macOS, every agent).
- Fixed (#24): `minigw run -- swift build` failed when the gateway's folder is on another disk than the system disk (for example `/Volumes/Java`): "unable to write manifest … You don't have permission to save the file" (Code 513), because macOS keeps save copies for that disk on the disk itself (`/Volumes/<disk>/.TemporaryItems/folders.<uid>/TemporaryItems`). The sandbox now allows only new `NSIRD_*` folders there, like on the system disk. `swift build|test|run|package` also get `--cache-path` in the run's temporary folder in Scratch, so SwiftPM's manifest cache works ("failed storing manifest … readonly database" is gone); its configuration and fingerprints stay read-only (the two "is not accessible or not writable" warnings stay, as do the harmless `xcrun_db` warnings). Mac app only.
- Fixed (#72): `minigw run -- xcodebuild -scheme … build` on a Swift package (no `.xcodeproj`) failed with exit 74: "Could not resolve package dependencies: cannot open file '~/Library/Caches/org.swift.swiftpm/manifests/ManifestLoading/….dia' (Operation not permitted)" and "Failed saving result bundle … in the folder T". ## 0.5.22

- Fixed: in worktree mode the agent's `git status` no longer shows an untracked `.build/` folder (the gateway's temporary folder in the clone; both gateways).
- Known limitation: in worktree mode an agent cannot create its own git repositories inside the clone (`git init`, `git clone`, CMake FetchContent with git sources). Build those dependencies in sync mode, or fetch them before the run; a shared dependencies folder for agents comes in 0.5.23.
- Fixed (#62): over SSH, `minigw gw` could unlock the login keychain with any password, because macOS does not check it while the keychain is unlocked, even when it reports it as locked for the SSH session. Now it asks only when macOS reports the keychain as locked, checks the password against the Mac account (Open Directory) before unlocking, and makes sure the keychain is really unlocked afterwards; a wrong password ends with "wrong password: the keychain stays locked", and separate messages cover a password that cannot be checked or does not unlock an out-of-sync keychain. When the keychain is unlocked but the admin item still cannot be read, it asks to quit and open the Mini Gateway app once on the Mac; without a terminal it suggests running `minigw gw` in an interactive SSH terminal before `security unlock-keychain` (macOS only; the Go client has no Keychain admin path).
- Fixed (#63): the Claude Code plugin stayed on an old version (for example 0.5.19 after installing 0.5.21), because Claude Code auto-updates third-party marketplaces only when `autoUpdate` is set. The plugin now updates automatically from the `release` branch, which only a release moves: `minigw plugin install` (Homebrew cask, MSI, `install.sh`) adds the `mini-gateway` marketplace with `"ref": "release"` and `"autoUpdate": true`, and updates the entry that minigw 0.5.21 or older added; an entry you changed (your own `"autoUpdate": false`, another `source`) stays. To opt out, set `"autoUpdate": false` under `extraKnownMarketplaces` → `mini-gateway` in `~/.claude/settings.json`. By hand: `/plugin marketplace add gh-commiter/mini-llm-gateway#release`. `minigw plugin uninstall` removes both forms. `minigw plugin status` prints `claude plugin marketplace update mini-gateway` and `claude plugin update minigw@mini-gateway` when the installed plugin is older than minigw. Both clients, compatible with the Claude Code CLI.
- Fixed (#64): `brew upgrade` printed that the plugin was "added" although it was already there (the old cask removed the entries before the upgrade). The `minigw` cask now leaves them on upgrade and reinstall, so `minigw plugin install` reports "already in"; this takes effect from the upgrade after 0.5.22, since an upgrade runs the old cask's uninstall step. The Windows MSI no longer runs `minigw plugin uninstall --upgrading` on an upgrade either (`--upgrading` is still accepted). The cask caveats now list exactly what `brew uninstall --zap --cask minigw` removes (without asking, as before) and say "gateway Mac" instead of "router Mac".
- Fixed (#65): `minigw plugin uninstall` ran `claude plugin marketplace remove mini-gateway` even when the `mini-gateway` entry was your own (another `source`, your own `ref`, `autoUpdate` false), although the settings cleanup keeps it; now the Claude Code removal runs only for an entry minigw added (both clients). On a Windows MSI upgrade where you untick the "Claude Code plugin" feature, the plugin entry is now removed (before, it stayed against your choice); an upgrade of an install that never had the plugin part (for example `/minigw:gw update`) leaves a plugin you added by hand alone.
- Fixed (#60): when the gateway caps an agent's work mode (#45), minigw's start line said "read-write" and only the gateway note on the first request said the agent "only read the folder". The gateway now lists the capped agents when it registers the folder, so the start line says "syncing … read-write (read-only for Codex: capped by the gateway)", or "read-only (capped by the gateway)" when every agent is capped; in native mode in the folder itself the line ends with ", read-only for Codex (capped by the gateway)". With an older gateway the line stays as before. Both gateways, both clients.
- New (#60): `minigw gw claude|codex|grok|copilot --work=direct|sync|worktree` sets the agent's cap from the command line (as in Settings, the settings page and `minigw gw settings`); without `--work` it shows it, and `minigw gw claude` now also prints `work`. Any other value: "--work: direct, sync or worktree"; `--work` with another command: "--work only applies to minigw gw claude|codex|grok|copilot". Mac app and `minigw serve`.
- Security (#59): a gateway Codex run could load a `.codex/config.toml` from the clone or shared folder (written by the agent or the client) when you trusted that project, its repository or a folder above it in `~/.codex/config.toml`, and its `notify`, `mcp_servers` or hooks then ran outside Codex's sandbox. Now every gateway Codex run (chat, sync, direct, worktree and native mode, resumed sessions, nested agent calls, and the model list `codex debug models`) marks its folder and every folder above it as untrusted for that run, so Codex ignores project settings there (on Windows also through junctions); your `~/.codex/config.toml` itself still applies. Mac app and `minigw serve` (Windows, Linux, macOS).
- Security (#61): in worktree mode the gateway refuses to start an agent (also an agent asked by another agent) when a new `.git` appeared in its start folder in the clone or a folder above it (other than a registered nested repository's), or one of those folders was replaced by a link: "The agent's clone was changed (a .git appeared at <path>): start a new conversation" (400). Nested repositories already in your folder keep working across turns. The agents' git in the clone no longer uses a bare repository it finds by itself (`safe.bareRepository=explicit`), and an agent asked by another agent is refused when the caller's clone `.git` was replaced, like the caller itself. Mac app and `minigw serve` (macOS, Linux, Windows).
- Fixed (#66): in worktree mode, each `minigw -p --continue` (or `--resume <id>`) turn started from your folder, which the agent's previous branch does not change, so the agent did not see the files it said it had made. Now the next turn of the same conversation always starts from the conversation's last branch, also when your folder changed since the last turn (minigw then prints "minigw: worktree: continuing from minigw/…; changes in your folder since the last turn are not in the agent's copy"), and its branch contains the earlier turns; the branch line says "(<base> = your state when this conversation started; this branch includes the earlier turns)". `--continue` takes the last conversation minigw ran in this folder, `--resume <id>` that session, whose branch name then moves forward (`--continue` gets a new branch each turn); `--resume <id> --fork-session` continues from that session's branch as a new conversation; `--resume` without an id starts from your folder. All agents of one run start from the same point; the next turn continues from the branch that came back last. It starts from your folder, with "minigw: worktree: starting from your folder, not from minigw/…: <reason>", when you deleted the branch (delete it to start fresh), when the conversation ran on another gateway, or in a repository with nested repositories; a branch you merged into `HEAD` starts from your folder without a line. minigw keeps the last branch per conversation in `.git/minigw-continue.json`. minigw on Mac, Windows and Linux; no gateway change.

- Inside a gateway agent (`MINIGW_AGENT_URL`), `minigw plugin` and `minigw uninstall` are refused like `connect`, `reconnect`, `disconnect` and `profiles` (both clients).
